1. Background

The product is a resin (photopolymer) 3D printer. Your team develops the main system (RPi 4 / RPi 5). Phrozen is responsible for the subsystem board, which receives slice images, drives the LCD, and controls the UV LED.

USB role limitation: You would like to connect over USB 2.0. The SoC vendor has confirmed that the SSD202D USB controller supports Host mode only and cannot be switched to Device mode, so the subsystem board cannot act as a device on the RPi's USB host ports. The two options below address this limitation.

Without compression, the transfer time in either option may exceed the per-layer print cycle. We recommend also evaluating compression such as RLE (slice images usually compress very well) and double buffering, so the next layer is transferred during exposure and lift.

2. Option 1: RPi connects directly to the FPGA via SPI

The SoC is removed. The RPi sends images directly to the FPGA over SPI, reusing the existing FPGA commands for LCD control.

2.2 Changes required on your side

AreaDetails
Hardware
  • For mass production, an adapter board is needed to route SPI out (jumper wires are acceptable for testing only)
  • Please review current RPi GPIO usage: besides SPI0 (GPIO 7–11), we recommend reserving 1–2 GPIOs for busy/ready or interrupt signals, since SPI has no flow control
  • Cable length and connector quality must be controlled; board-to-board SPI is sensitive to signal integrity at high clock rates
Software
  • Use the spidev driver and increase spidev.bufsiz (default is only 4 KB per transfer)
  • Implement the agreed transfer protocol, including ack and CRC error checking
System partitioningControl functions previously handled by the SoC must move to the main system or the FPGA (to be discussed)

3. Option 2: RPi USB Gadget connected to the SoC

The existing subsystem architecture is kept. The RPi's Type-C port is switched to USB Device (Gadget) mode and connected to the SSD202D's USB Host (Type-A) port.

3.2 Changes required on your side

AreaDetails
Software
  • Add dtoverlay=dwc2,dr_mode=peripheral to config.txt and load the Gadget module
  • Update the image transfer program to send data through the Gadget interface
Power
  • The Type-C port is normally the RPi's power input. Once it is used for data, we recommend a Y cable that separates power and data:
    • Power branch: VBUS, GND, CC (a Type-C power supply only outputs power after detecting the RPi's CC pull-down; RPi 5 also uses CC for PD negotiation)
    • Data branch: D+, D−, GND
  • Powering via the GPIO 5V pin is not recommended, as it bypasses the RPi's power protection circuitry, unless your power board provides its own protection
  • RPi 5: without a 5V/5A PD supply, USB output current is limited to 600 mA. Use a PD-capable Y cable, or set usb_max_current_enable=1 in config.txt
Phrozen-side measure: To prevent back-feeding between the SoC host's 5V output and the RPi supply, the subsystem board will remove the VBUS output on its USB port (via a 0Ω resistor, so it can be restored for normal host use such as firmware updates). The setup therefore works whether or not the Y cable's data branch carries VBUS.
