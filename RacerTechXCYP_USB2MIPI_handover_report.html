USB2MIPI 光引擎板交接整理

彙整奔馳科技（Racer Tech）提供的開發成果與交接文件，作為我們把設計轉給下一家廠商打樣與生產時的依據。重點放在「要交什麼、哪些已定案、哪些還沒定、哪些文件彼此矛盾」。

整理日期 2026-10-06 研發廠商 奔馳科技 Racer Tech 交接文件指定接手方 西柏科技 Cypress 終端客戶 Stratasys

摘要

這個專案是光固化 3D 印表機的「光引擎」：上位機用 Python 把切層影像經 USB 2.0 送進 FPGA，FPGA 再經 MIPI 推到 mask LCD 曝光。硬體上分成兩塊板：

  • XCZU1CG 核心板（Xilinx Zynq UltraScale+）：跑 Racer 開發的 Vivado 硬體設計與 Vitis 韌體。核心板本身沒有電源管理晶片（PMIC）。
  • 供電載板：把 12–24 V 轉成核心板要的 6 條邏輯電源與 3 條面板偏壓，經 30-pad 的 J1 邊緣送進核心板；同時把 USB、UART、debug 拉到 header。這塊是接下來要請新廠商畫原理圖、Layout、打樣的板子。
12–24 V寬輸入、單一電源接頭（Micro-Fit 3.0）
6 + 3邏輯電源軌 + 面板偏壓軌
≈ 8.9 W穩態總功耗（核心板 + 17″ 面板）
< 3.5 A開機湧浪上限（客戶線上保險絲）
接手前最要注意的三件事

① 交接文件第 9 節的參考電路圖 v1.1 Sheet 1 是雙輸入版本，已於 2026-07-05 取消，不能照圖施工。② 面板偏壓與 1.8 V 裕度還缺三種新面板的資料，其中面板資料由我們（普羅森）負責提供，而且會擋住 Layout。③ 客戶要求影像從 3-bit 改 6-bit，單張資料量約倍增，這會動到韌體與協定；目前拿到的 PDF 說明仍是 37.56 MB 的舊版本。

2軟體與通訊協定

出自「USB2MIPI 嵌入式顯示系統使用說明.pdf」第 1–4 節。

影像與記憶體規格

平台Xilinx Zynq UltraScale+（ZynqMP），PS + PL
影像格式24-bit RGB BMP，原始解析度 1668 × 7500
左右分割軟體拆成左右兩通道，各 834 × 7500；兩側各補 2 Bytes padding，使每行記憶體跨距為 2504 Bytes（DMA 對齊）
動態 ID 注入把層數 img_index 寫進左通道第一行的 padding（2 Bytes），讓每層 32-bit checksum 唯一；不影響實際投影像素
單張傳輸量固定 37,560,000 Bytes（= 2504 × 2 × 7500）
硬體緩衝DDR 內 FIFO，最多 10 個 slot，可非同步預載
黑盒子暫存器PL 端 AXI4-Lite，位址 0x80040000，獨立於 APU 軟重置網域，當機時資料不流失

USB 與 Python 環境

介面USB 2.0 High-Speed，FPGA 為 Device
裝置識別VID 0x8888、PID 0x9999
資料端點EP_OUT 0x01，Bulk Transfer
Python 套件pyusb（usb.core / usb.util）、libusb_package、numpy
本地資料庫執行目錄下自動讀寫 checksum_database.json，記錄 checksum 與檔名的對應，供斷點續印

指令表

按鍵指令碼行為
w0xA2 Write送出上傳準備通知，經 Bulk OUT 把下一張 BMP 寫入 FIFO
p0xA3 Start啟動曝光：把 FIFO 最舊的切片推上畫面，checksum 寫入黑盒子鎖定
s0xA4 Stop立即停止曝光，一幀內切黑畫面，回到空閒
d0xA5 Pop釋放上一張已曝光切片的 FIFO 空間，指標前進一格
c0xA0 Clear清空 FIFO，讀寫指標歸零
r0xA7 Reset硬體管線深度重置（含 LCD 放電與 MIPI 核心重啟），約 4.5–5 秒；軟體同步重置 USB
i0xB0–0xB4讀取狀態：FIFO 剩餘空間、已印層數、韌體版本、錯誤碼
k0xB3讀取即時影像 checksum，與上位機佇列比對
b0xB4讀取黑盒子記錄的最後一次 checksum
f0xA6注入硬體斷流，測試異常攔截
t / tN自動排程自動壓力測試；t1.5 表示每層曝光 1.5 秒連續測試
q離開關閉背景監控執行緒並結束

錯誤碼與災難復原

錯誤碼名稱硬體行為
0x01Buffer UnderflowFIFO 無資料仍啟動投影 → 攔截，防止空曝
0x02Buffer Overflow10 個 slot 已滿 → 拒絕寫入直到釋放
0x03MIPI FaultMIPI 斷流 → 一幀內切黑、鎖死管線、拒絕所有指令，必須硬體重置
0x04Hardware Resetting重置期間所有外部指令被擋
  • 看門狗：Python 背景執行緒每 0.5 秒查詢 0xB2；偵測到 0x03 自動用 0xB4 撈黑盒子 checksum 並印出對應檔名。
  • Bulk 超時：37.56 MB 傳輸超時固定 30,000 ms。
  • 重置驗證：重置後每 0.5 秒輪詢，最多 15 秒（30 次），未恢復即判定逾時。
  • 斷點續印：當機後依畫面印出的最後檔名，機台重新上電後從該層接續。

3韌體燒錄與環境設定

出自 PDF 第 5–7 節。量產時的燒錄流程會以 QSPI 方式為基礎。

JTAG 開發燒錄

  • Vitis 建 Application Project，匯入 Vivado 產生的 .xsa；確認 BSP 後 Build 出 .elf。
  • Boot Mode 切 JTAG，接好 JTAG 與 UART；Run As → Launch on Hardware (Single Application Debug)；看 UART Console 確認 PS 與 PL 喚醒。

QSPI Flash 脫機啟動

  • Xilinx → Create Boot Image，依序加入 fsbl.elf、FPGA 位元流 .bit、應用程式 .elf，產生 BOOT.BIN。
  • Xilinx → Program Flash，Image File 選 BOOT.BIN，FSBL 選 fsbl.elf，Program。
  • 完成後斷電、Boot Mode 切 QSPI，重新上電即脫機執行。

Boot Mode 開關（SW1[0:3]）

模式SW1[0:3]
JTAG0000
QSPI0010
SD Card0101
eMMC0110

注意：這裡的 SW1 是開發板的 Boot Mode 開關，和供電載板文件中的 SW1（面板高壓手動切斷）是不同東西，位號重複。

Windows USB 驅動（Zadig）

用系統管理員身分執行 Zadig → Options → List All Devices → 找 VID 0x8888 / PID 0x9999 → 換成 libusb-win32 或 WinUSB → Replace Driver。Python 印出 “Device connected” 即成功。

目前 USB 是飛線

PDF 第 7 節的照片顯示：開發板上的 USB 2.0 是從 FPGA 直接焊跳線出來，沒有經過 IO 板上的 USB Hub。遇到 USB connect error 要先查跳線是否斷路。量產板必須把這段改成正式走線（見第 6 節 R4）。

6生產前風險與待辦

R1–R4 是交接文件 §11 列出的待決事項；R5 以後是比對三份資料後，我們這邊額外看到的落差，建議在發包前和 Racer 或新廠商確認。

  1. 三種新面板的偏壓電壓與 source-driver 電流擋 Layout負責：普羅森

    7.1″ 8K（群創）、10″ 16K、13.5″ 16K 的數值還沒提供。大尺寸面板電流較高，要據此重算面板偏壓與 1.8 V 裕度。目前規格是依 Innolux 9.55″ / 17″ 算的。

    由我們（交接文件寫 Darrell / Katel）盡快向面板廠取得規格，並同步給 Racer 與新廠商。

  2. 1.8 V DC-DC 最終定額影響選型負責：Racer

    取決於 PS-GTR link speed 與 lane 數，目前建議 ≥ 3 A。

    請 Racer 在結案前書面回覆。

  3. Micro-Fit 接頭出線方向影響機構負責：Stratasys / 普羅森

    板端 43650-0200 是直角 header，需和客戶機構確認方向。

  4. 風扇軌規格未定影響 BOM負責：普羅森

    J14 需獨立穩壓軌或 PWM buck，電壓與電流還沒定。

  5. JP1 面板選擇只涵蓋 9.55″ / 17″文件不一致

    07-05 已把面板清單改成 7.1″ / 10″ / 13.5″，但 JP1 仍是兩段式（9.55″ 或 17″），PANEL_ID 只能表示兩種面板。三種新面板需要至少 2 bit 的識別，韌體的面板時序選擇也要對應。

    確認新面板清單後，請 Racer 決定 PANEL_ID 改成幾位元，以及韌體是否要跟著改。

  6. 影像 3-bit → 6-bit，單張約 75 MB韌體與協定變動負責：Racer

    交接文件說這不影響供電板，但會改到 USB 封包定義、DDR FIFO 槽數與韌體時序。我們拿到的 PDF 說明仍是固定 37,560,000 Bytes、10 個 slot、30 秒超時的版本。若保持 10 個 slot，FIFO 需要約 750 MB DDR，要確認核心板 DDR 容量夠不夠；傳輸時間約倍增，30 秒超時與曝光節拍也要重新驗證。

    確認 6-bit 版本是否在 Racer 的交付範圍內，以及收到的 USB2MIPI17 原始碼是哪一版。

  7. USB 目前是飛線，量產要正式走線Layout 注意

    開發板上 USB 是從 FPGA 直接焊跳線。量產載板要把 J3-4/5 拉到 J11，以 USB 2.0 HS 規範走 90 Ω 差動對並加 ESD。這段沒有經過完整的正式走線驗證。

    Bring-up 項目加入 USB HS 長時間傳輸測試（例如用 t 壓力測試跑數千層）。

  8. 交付檔案是否收齊待確認

    交接文件 §10 列了 KiCad 原理圖、Netlist、Spec v2.0（中英）、Core Board Datasheet v1.2、USB Protocol Specification、面板規格、IOB 1V1 DSN、Stratasys 輸入級參考圖。目前 RacerTech_provided 與上層資料夾裡只看到 USB2MIPI17 專案（含 .xsa），沒找到上述文件。

    向 Racer 索取完整清單內的檔案，再一起轉給新廠商。

  9. 量產燒錄與測試治具不在範圍內需另外規劃

    交接範圍排除了量產測試治具與認證。量產時每片核心板都要燒 BOOT.BIN 到 QSPI 並切 Boot Mode，目前只有手動的 Vitis 流程；認證（CE / UL / FCC）也沒人負責。

    和新廠商討論量產燒錄方式（例如治具加批次腳本）與出貨測試項目；認證由誰負責要另外決定。

  10. 開機湧浪必須實測Bring-up 必驗

    客戶線上是 3.5 A 保險絲，soft-start 沒壓好會在客戶端跳保險絲。要在 12 V 與 24 V 兩種輸入下都量測。
